# Dark Store Management System — Project Guide

## 1. Project in one sentence

A small quick-commerce system that helps a single dark store manage its product catalogue, store-level stock, customer orders, rider assignments, and low-stock alerts, with PostgreSQL as the main academic focus.

## 2. Stack and architecture

- **Database:** Supabase PostgreSQL
- **Authentication:** Supabase Auth
- **Frontend:** React (Vite) with plain, separate CSS files
- **Database access:** Supabase JavaScript client from React, protected by PostgreSQL Row Level Security (RLS)
- **No separate Express server in the first version.** Add one only if the professor requires server-side API code.

```text
React pages and components
        | Supabase client + signed-in session
        v
Supabase Auth and PostgreSQL
        | tables, constraints, transaction function, trigger, view, RLS
        v
Dashboards and reports
```

Supabase uses PostgreSQL, so translate the source brief's MySQL-specific syntax: `AUTO_INCREMENT` to identity columns, `ENUM` to `CHECK` constraints (or PostgreSQL enums), MySQL trigger syntax to a PostgreSQL trigger function plus trigger, and `START TRANSACTION` examples to a PostgreSQL function or transaction executed through an appropriate server-side connection. For the app, RLS is the practical role-aware database security feature. Supabase recommends enabling RLS for exposed tables and combining policies with Auth. [Supabase RLS guide](https://supabase.com/docs/guides/database/postgres/row-level-security)

## 3. Keep the scope small

Build a **single-store demo** with three user types: manager, rider, customer. Keep `zones` and `dark_stores` in the schema for the ER diagram and future multi-store extension, but seed one zone and one store. Do not build payments, maps, live GPS, notifications, multiple branches, or a complicated admin system.

### Pages

1. **Home:** project name, brief purpose, key features, and three role cards/buttons.
2. **Login:** selected role is shown; email/password sign-in.
3. **Manager dashboard:** summary cards, inventory table, low-stock alerts, recent orders, and simple reports.
4. **Rider dashboard:** assigned orders and a status update action.
5. **Customer dashboard:** product list, stock display, cart, and order history.

Use a clean sidebar/header for dashboards, readable spacing, a restrained palette, clear status badges, and responsive tables/cards. Use plain CSS in files such as `src/styles/global.css`, `src/styles/home.css`, and `src/styles/dashboard.css`; do not use Tailwind or inline style blocks.

## 4. Database design

Use these ten tables from the supplied brief. For the shortest build, keep all ten but populate only the records needed for the demo.

| Table | Purpose and key design point |
|---|---|
| `zones` | Delivery areas; unique pincode |
| `dark_stores` | Store belongs to a zone; seed one active store |
| `categories` | Product category lookup |
| `products` | Product name, category, positive price, active flag |
| `inventory` | Store/product stock; composite primary key `(store_id, product_id)`; nonnegative stock and reorder threshold |
| `customers` | Customer profile linked to Supabase Auth user and zone |
| `riders` | Rider profile linked to Auth user and store; status constrained to allowed values |
| `orders` | Customer, store, optional rider, status, total, lifecycle timestamps |
| `order_items` | Composite primary key `(order_id, product_id)`; positive quantity and `price_at_purchase` snapshot |
| `restock_alerts` | Store/product and stock snapshot; nullable `resolved_at` |

### Academic design points to be ready to explain

- **1NF:** order lines are rows in `order_items`, not comma-separated products in `orders`.
- **2NF:** `inventory.current_stock` depends on both columns in its composite key; order-item values depend on the order/product pair.
- **3NF:** customer, product, category, and store facts live in their own tables rather than being repeated in orders.
- **Integrity:** primary keys, foreign keys, `UNIQUE`, `NOT NULL`, and `CHECK` constraints protect valid data.
- **Historical price:** `price_at_purchase` preserves the price used when the order was placed.
- **Inventory correctness:** stock is per store and product; it cannot be negative.

Use `GENERATED BY DEFAULT AS IDENTITY` for numeric IDs, `NUMERIC(10,2)` for money, `BOOLEAN` for flags, and `TIMESTAMPTZ` for event times. Prefer `CHECK` constraints for small fixed status lists because they are easy to explain and edit.

## 5. Essential database features for the demonstration

Keep these DBMS features visible in named SQL files under `supabase/` or `database/`:

1. **Schema and constraints:** all core tables, keys, checks, and useful indexes.
2. **Seed data:** one zone, one store, a few categories/products, inventory, demo customer and rider profiles.
3. **Order transaction:** one PostgreSQL function that validates requested quantities, reduces stock, creates an order and order items, and fails completely if an item is unavailable. Explain that PostgreSQL functions execute within the caller's transaction; do not claim that separate browser requests form one atomic transaction.
4. **Low-stock trigger:** a trigger function inserts a restock alert only when stock crosses from above the threshold to at/below it. Avoid generating duplicates on every later stock reduction.
5. **View:** active orders with customer and rider details, or a low-stock inventory view.
6. **Reports:** at least three readable SQL queries: low stock, best-selling products, and store/order totals or rider delivery counts.
7. **Security:** Supabase Auth identifies the signed-in user; RLS policies restrict customer/rider rows and manager operations. A role selector in the UI is not security by itself. Keep any secret/service key out of React. Supabase documents RLS policies as database-side row filters and stresses the role grants plus policies together. [RLS guide](https://supabase.com/docs/guides/database/postgres/row-level-security)

For a mini project, use a simple `profiles` mapping from `auth.users.id` to an app role (`manager`, `rider`, `customer`) and optional customer/rider record IDs. Do not duplicate passwords in your own tables. Have the trigger use a PostgreSQL trigger function; PostgreSQL triggers require both the function and the trigger object. [Trigger guide](https://supabase.com/docs/guides/database/postgres/triggers)

**Transaction caveat:** a normal multi-step client workflow is not atomic. Keep order creation in one database function invoked with Supabase RPC, and design it so the function raises an error if stock is insufficient. If the function fails, its database changes roll back. Keep the function small enough to explain line by line.

## 6. Four-phase build plan

### Phase 1 — Database foundation

Create the Supabase project; write schema and seed SQL; make an ER diagram; inspect rows in the Supabase table editor. Confirm the composite inventory key and constraints.

**Done when:** the schema builds from a clean database and seed records appear.

### Phase 2 — Database logic and security

Add the order-placement function, low-stock trigger, one view, three reports, and simple RLS policies. Test the order function with enough stock and insufficient stock; verify stock, order, and alert outcomes.

**Done when:** the central DBMS concepts are demonstrable without the UI.

### Phase 3 — React UI and login

Build the home page and role selection, Supabase Auth login, shared dashboard layout, then the three small role dashboards. Put styles in separate vanilla CSS files. Connect only the pages needed for the demo.

**Done when:** each demo account reaches its dashboard and the dashboard loads role-appropriate data.

### Phase 4 — Demo polish and viva prep

Add loading/empty/error states, validate forms, run through the demo flow, prepare screenshots and ER diagram, and practice explaining normalization, transaction safety, trigger, view, and RLS. Keep a short fallback SQL demo in case internet access fails.

**Done when:** the full demo can be completed smoothly in a few minutes.

## 7. Suggested demo sequence

1. Show home page and explain the three roles.
2. Sign in as manager; show inventory, a low-stock alert, and one report.
3. Sign in as customer; place an order for an available product.
4. Show the order and the reduced inventory.
5. Try ordering more units than remain; show the clear failure and unchanged order/stock state.
6. Sign in as rider; update the assigned order status.
7. Point to the ER diagram and explain primary/foreign keys, composite keys, normalization, trigger, transaction, view, and RLS.

## 8. Avoid these scope traps

- Do not implement payment, maps, geolocation, real-time subscriptions, or a multi-warehouse routing algorithm.
- Do not build an elaborate design system or use Tailwind; use a small set of reusable CSS classes.
- Do not make the role cards on the home page grant access. They only choose the login path; the authenticated profile and RLS determine access.
- Do not store passwords in `customers`, `riders`, or `profiles`.
- Do not let the browser independently insert an order and decrement stock in separate calls.
- Do not add every optional table from the source brief. `order_status_history` and audit logs are future work.

## 9. Source brief mapping

The supplied document's core ideas are retained: store-level inventory, customer/rider/order data, order-item price snapshots, restock alerts, normalization, constraints, joins, aggregates, subqueries, views, triggers, transactions, concurrency, security, and a demonstration scenario. Its MySQL/InnoDB, Express, and Tailwind choices are replaced by Supabase PostgreSQL, Supabase Auth/RLS, React, and vanilla CSS. The multi-store design remains in the schema, while the first demo uses one store to keep the application and viva manageable.
